> 同一语义组内的多个标签必须合并进一次 LLM 请求——这是正确性要求，不是性能优化；拆批的代价是上下文丢失与判定不一致。历史记录中曾以 token −46.64%、0 次阈值跨越作为论据（该口径已被降级为副作用）。超限语义组仍由协议层自动拆分。

# 字面意思 vs 团队实义

- **字面意思**：按语义分组发请求，听起来只是一种组织方式。
- **团队实际含义**：**同一语义组内的多个标签必须合并到一次 LLM 请求里判定，不能拆成多次。** 拆开会导致**上下文丢失、判定不一致**。
- **易混淆点**：**这不是性能优化手段，是正确性要求。** 性能变化只是伴随现象。

# 定义

2026-10-22 起删除 `tag.lab.batch-size`(16) 与组内题数拆分，每个语义组（全场 / 每场景 / 每场景+维度）**一个 JEV 请求**。

# 立论是正确性，不是 token

删除 `batch-size=16` 拆批、改为每个语义组一个请求后，曾记录到输入 token −46.64%、阈值跨越 0 次。但按本条的定调：

| 曾经的论证方式（勿用） | 正确论证方式 |
|---|---|
| token 降了 46.64%，所以合批好 | 拆批破坏同组上下文，判定不一致，所以必须合批 |
| 0 次阈值跨越证明合批更优 | 0 次阈值跨越只是正确性约束下不应出现的噪声，是**副作用** |

⚠️ 用 token 数字为「合批」背书，会诱导后续按性能口径回退该决策——一旦某次测得 token 上升，就会有人主张拆批，把正确性约束当成性能开关拨回去。这是与 [[评测口径陷阱]] 同类的翻版错误。

## 口径分歧（两版记录并存）

- **旧版记录（`02-方案选型与权衡.md`）**：以「少用 46.64% 输入 token、0 次阈值跨越、准确率在噪声内」为主论据，结尾以用户自己的数字验收改动。
- **新版记录（`术语实义-补充测试.md`）**：明确本条立论为**正确性**，性能收益降为副作用，并把上表的 token 论证方式标为**勿用**。
- **处理**：两者不互相否定事实，只否定论证口径。下文的性能数字作为**已观测事实**保留，但不再作为支持本决策的理由；引用时须注明其为副作用。

# 意义（为什么拆批不行）

- 130 个维度里 90 个 >16 标签、16 个 >100、最大 314——按 16 题拆批会造成大量重复上下文，同组标签被切到不同请求中，判定不一致。
- [[JEV 推理服务]] 限额 64k/请求、32k/题，足以容纳整组。

# 历史性能数据（记录保留，勿作论据）

- 实测：314 标签组一个请求完成（输入 45,554 token，2,355 ms），比拆批**少用 46.64% 输入 token**，配对最大分数差 0.07，**0 次阈值跨越**。
- 验收（由用户自己的数字关掉）：新管线准确率 **84.9% / 绝对覆盖 65.9%**，vs 拆批 **85.2% / 66.1%**——在噪声内，改动保留，新管线成为新品牌基线。

# 代价 / 反例：边界是超限组仍会自动拆分

「一个语义组一个请求」不是绝对的「永不拆」。[[jev-推理服务]]（即 [[JEV 推理服务]]）有单请求 64k、单题 32k 的限额，**超限的组仍会自动拆分**——这是协议层的硬边界，不违背正确性要求（同组内容仍尽量同请求）。协议见 [[四段结构协议]] / [[四段结构-jev-noul-v1]]。

实现上（10-26 `d504c9f`）：由 `LabBatchPlanner` 把超过上限的组切成**最少的连续子请求**（详见 [[打标系统]]）。

根因值得记：314 题组失败**不是图片、不是标签备注**，而是 label v11 让每题约 341 字符，估算 81,317 token 超过 64k；早期「62k + 1.5k 图片」的猜测是错的。

# 与「取消维度阶段」的口径区别

[[取消维度阶段]] 也是一次「token 变化」的改动，但它是**收益驱动**的取舍（token ×2 换回 565 个被门挡掉的标签）；本条是**正确性驱动**的约束。两者的 token 口径不可互借，不可互相引用对方的变化幅度作论据。
