> 三批来源材料（C/D/Z）冲突时的五项裁决规则，规定代码、文档、会话三层可信度顺序以及冲突的落地处理方式。

# 定义

仲裁口径是团队对「同一事实存在多份互相冲突的记录时，应该采信哪一份」的约定。它针对的是本项目两个月内多次改向、同一结论在不同时间点可能正好相反的现实：**引用任何结论之前必须先确认口径与版本**。

# 五项规则

## 规则 1：代码 > 文档 > 会话

```
当前仓库代码  >  docs/ 里的 Spec  >  会话/记忆里的描述
```

**范式案例（[[租户上下文]]）**：

- `[Z]`（2026-10-29 记录）与 `[D]`（11-03 会话）都说 `global:dynamicTenant:<userId>` 按 userId 而非会话隔离；
- `[C]`（Codex，贴近当前代码）说「已合入按登录会话隔离」；
- 查代码：`TenantHelper.java:37` 是 `DYNAMIC_TENANT_SESSION_KEY`，`:41` 注释「已不参与读取，只在注销与重置时清理残留，避免旧值误导排查」，`:43` 是 `LEGACY_DYNAMIC_TENANT_KEY`；
- **裁决**：以代码为准，`global:dynamicTenant:*` 已失效。

## 规则 2：时间近的 > 时间远的，但按事件类型区分

| 事件类型 | 判据 |
| --- | --- |
| 架构决策（阶段数、协议、阈值默认值） | 取最新 |
| 一次测量结果 | 取当时的；不要用新代码否定旧测量 |
| 失败教训 | 永久有效，除非明确修复 |
| 环境/网络问题 | 只在当时环境有效，换机器/换网络要重测 |

**范式案例**：`[Z]` 说「ACR 上传 ~0.2 MB/s 是实例侧带宽配额」，`[D]` 说「宿主 docker push 被代理掐断」。两者都对，只是不同时间、不同现象：前者测的是 ACR 容量上限，后者记录的是代理链路断连。**都保留，标注适用条件。**

## 规则 3：批次冲突先看是不是「同一件事的不同阶段」

**范式案例（[[阶段演进]]）**：`[Z]`（10-26 前）是三阶段 scene / dimension / label；`[D]`（11-05 后）与 `[C]` 是两阶段 scene / label。**这不是矛盾，是演进**：新文档写「两阶段（11-05 起）」，同时保留三阶段的历史章节，因为老 Spec、老导出数据、老评测基线仍按三阶段组织。

## 规则 4：数字冲突先查分母与口径

| 场景 | 常见口径差异 |
| --- | --- |
| 准确率 | strict vs inference；unknown 是否入分母；直标 vs 含补全 |
| 召回 | 维度门是否算分母；冻结图谱版本 |
| 耗时 | 单件 vs 整批；含不含图片下载；哪个 commit |
| token | 输入 vs 输出；含不含重试与补问 |
| 准确率对比 | 同场景 vs 混合；样本构成 |

**范式案例（[[判分口径]]）**：`87.4%` vs `84.9%`——前者是 RL 100 混合场景，后者是 Zara 79 四场景，**不能直接比**。

## 规则 5：无法裁决时两个都写出来并标注冲突

不强行统一。此类条目统一收进 [[未决与空白登记]]，格式为：

> 「A 说 X（时间/来源）/ B 说 Y（时间/来源）/ **当前无法裁决，因为 Z**」

# Significance

- 这是整套 wiki 的**前置条件层**：任何页面引用某个数字或结论时，都必须能回溯到符合仲裁口径的版本。
- 它与 [[三批材料的权威分工]] 互补：后者回答「谁对什么主题权威」，前者回答「权威冲突时怎么裁」。
- 它是 [[引用标注规范]] 的推理基础：因为口径会变，所以引用必须带日期与口径标注。
