> 固定格式「试了什么/结果/根因/现在做法/代价」+ ⚠️ 标记当前缺口 + 出处分级，是本文档的方法论元层。

# 定义

失败知识归档规范规定了如何记录「被推翻的做法」，使后来者能判断一条结论是实证、推断还是猜测。

# Schema

## 记录格式（五段）

1. **试了什么** — 当时的假设与做法
2. **结果** — 可量化观测（pp / token / 条数 / 百分比）
3. **根因** — 机制层解释
4. **现在的做法** — 回滚或替代方案
5. **代价** — 遗留成本或未修缺口

## 标记约定

- **⚠️** 用来标记「**已知未修**」——是**当前仍存在的缺口**，不是历史教训。缺口索引见 [[已知未修缺口清单]]。
- 出处分级：`[C]` Codex 会话导出、`[D]` DSH 会话导出（11 月权威）、`[Z]` zcode 记忆（10-19~11-02 权威）。逐条原文见 `evidence/`（待入库）。

# 重要性

1. **失败知识的价值高于现状描述**：仓库文档只写「现在怎么做」，不写「为什么不那么做」。
2. **防止元错误**：A9 中「精简版定义」实为「定义清空」，一旦命名错误，后来所有引用都会错——命名错误比技术错误更危险。
3. **防止归因错误**：结论必须标明是「数据能证明的」还是「推断」（A4 中「模型缺判据」被降级为假设）。
4. **防止把缺陷当现象**：D14 四处误判（NAT 出口被当成外部实例写库、详情图 `status=0` 被当成转存停滞、`global:dynamicTenant` TTL=-1 串租户、SQL diff 只看一半）的共同教训是——**先证明现象是缺陷，再找根因**。
