> 配额按用户而非按 key（恒定 100 并发），503 model_not_found 是网关通道冷却或上游熔断而非模型下线。

# 定义

并发与限流涉及三件事：我方并发度设置、上游（模型网关）的配额维度、以及失败信号的正确解读。

# 重要性

并发是**最容易通过调参造成事故**的旋钮：一次从 1 拉到 10，30 秒内打掉 57 条真实商品消息。

# Schema：实测记录

| 场景 | 设置 | 结果 |
| --- | --- | --- |
| 并发实验 | 1 → 10 | `HTTP 503 model_not_found No available channel`；13:14:32~13:15:01 **57 条真实商品消息全失败并转死信**（B3） |
| 复核 | 并发 2 跑 30 分钟 | **0 失败** → 503 更像**偶发上游渠道熔断**，与并发不完全线性 |
| 实验台 | `tag.lab.concurrency=20` | 4 个实例共 **46 次 429**，退回 10（B6） |
| 判分模型 | 24 / 20 / 12 / 8 | 180s 超时 / `HttpConnectTimeout` / 级联失败 / **8 + 一次网络重试全部完成**；17 次重跑多花 4.5M token |
| 加 key | 单 key 40 并发小请求 | **全部 200** |
| 配额口径 | —— | **不按 key 分，按用户分**：不管给多少 key，都只有 **100 并发**（B4） |

# 关键判断

- **503 ≠ 模型下线**：同一把 key 直接打网关是通的，`/v1/models` 里也在；10 并发瞬间把网关**通道打到冷却**。
- 加 key 解决不了限流——**先确认限流维度（per-key 还是 per-user），再谈加资源**。
- 并发是把双刃剑：配合「无 DLX」时，失败即永久丢失（B3 → B5）。
