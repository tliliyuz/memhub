> recoverTenant() 在一个事务里处理整批事件导致加锁顺序成环、28% 死锁；改用非锁定读 + DeadlockRetry 缓解但根因未改。

# 定义

事务边界指一次数据库事务覆盖的业务范围；边界过大时，锁持有时间变长、加锁顺序出现环的概率上升，进而触发死锁。

# 重要性

这是本系统中**唯一定量到百分比**的稳定性缺陷（28%），并且演示了「缓解 ≠ 根治」。

# Examples：一次真实死锁

- **现象**：完成路径加 `FOR UPDATE` 后，发版后 7 次完成里踩中 2 次（约 **28%**），「不是偶发」。
- **现场**：`SHOW ENGINE INNODB STATUS` 抓到加锁顺序成环——(1) 持 `tag_product` 行锁等 `tag_field_config` 行锁；(2) 持 `tag_field_config` 行锁等 `tag_product` 同一行。
- **根因**：`recoverTenant()` 是 `@Transactional`，**一个事务里循环处理一批事件**，锁范围过大。
- **修法**：认领/提交改用**非锁定读** + `DeadlockRetry`（3 次线性退避）→ 28% → **0%**。
- **⚠️ 遗留**：`recoverTenant()` 一事务处理整批的问题**未改**（G8）。

# 相关联的问题

- `TagMqRejectionRecorder` 的 `@Transactional` 把「拒绝跳过」变成「停消费者」（G3）——同样是事务边界越界。
- 部分更新接口误当 PATCH（D7）、裸 SQL 改写绕过审计字段（D6）都属于「写入路径的语义不清晰」。
