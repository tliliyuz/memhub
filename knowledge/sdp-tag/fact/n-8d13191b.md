> 先证明是缺陷→定位最小区间→找唯一能解释全部现象的假设→隔离环境验证→修复后复查原始症状。

# Definition

一个可复用的排查范式（手册第 7 章），也是全部失败类概念的导航枢纽。

1. **先证明是缺陷**（对照基线、复现、排除误判）——记录里 **4 次误判都发生在跳过这一步**。
2. **定位到最小区间**（哪条消息、哪个任务、哪个阶段、哪个时间点）。
3. **找「唯一能解释全部现象」的假设**（例：一起解释 C1~C4 的「品牌映射只认三个」）。
4. **在隔离环境验证**（临时队列、影子 vhost、限 1 件冒烟）→ 见 [[环境隔离与串环境事故]]。
5. **修复后复查原始症状**（不是只看新日志好看）。

# Significance

- 它把「急于给出解释」的失败模式显式化：先判断是不是缺陷，再谈根因。
- 步骤 3 的「唯一能解释全部现象」是排除竞争的硬约束，能避免并列多个互斥假设长期并存。
- 步骤 5 与[[静默失败]]的分层原则呼应：「有告警 ≠ 修好了」。

# 关键取证手法：雪花 ID 与进程识别

判断「有别人在写这个库」：

```
worker = (id >> 12) & 31
dc     = (id >> 17) & 31
```

实例：任务是 `worker 16/15`、`4/15`，当前 Pod 是 `14/19`；`config_hash` 是 `1b5bb6…`，当前 Pod 是 `0b544f…` → **另一份旧配置的进程**在写同一库。

⚠️ `49.235.144.47` 是**本 pod 的 NAT 出口**，别当外部实例。
