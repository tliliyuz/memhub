> 回写/补偿（免费幂等）/重放/重排队（真花钱）/强制重跑（全价）四类成本差异；改阈值不自动全量重打。

# 重跑动作体系

## 定义（实义）

本批材料里「回刷」只出现 1 次，指**全量重跑**。团队实际用五个词，成本完全不同，别混：

| 词 | 实际动作 | 成本 |
| --- | --- | --- |
| **回写 / 回调** | 我方 → 对方 `recover .../callback/v2` 的结果 POST | 几乎为 0 |
| **补偿 / compensate** | `POST /tag/event/compensate?limit=`，纯物化，**免费、幂等** | 0 |
| **重放 / replay** | `POST /tag_mq_rejected/{id}/replay`，重跑**原始报文**入库 | 低 |
| **重排队 / requeue-failed** | `POST /tag/event/requeue-failed?limit=` | **真实消耗模型费用** |
| **强制重跑 / force** | `POST /tag/task/product/{productPk}?force=true` | 全价 |

## 关键结论

- **改阈值后不会自动全量重打**，与 MQ 规则一致（事件到达才重打）。而调阈值会让 `configHash` 变化导致缓存失效，见 [[指纹与哈希复用]]、[[阈值体系]]。
- **任务级重跑 = 从场景阶段整体重跑**，不是「从失败的那个批次接着跑」，见 [[打标阶段模型]]。
- 存量成功结果没有 `inputHash`（`tagged_input_hash` 为空）→ 一律 stale，需显式触发（`force`）才重跑。

## 易误解

- 「回调成功」只代表 HTTP 通了；**落库是 [[对方 search 服务]] 的动作**。
- 把 compensate 当作重打：它是物化，不调模型。
- 用 requeue-failed 做「便宜重试」：它真花钱。

## 接口族汇总

`tag_mq_rejected/{id}/replay` · `/tag/event/compensate` · `/tag/event/requeue-failed` · `/tag/task/product/{pk}?force=true`
