> 标签下游落库方，写死品牌映射并在业务失败时仍返回 HTTP 200，是「假成功」的主要来源。

# 定义

kind: external_system

对方 V2 回写系统是我方标签的下游落库方，接收打标结果并按品牌写入对应租户库表。其返回语义与落库规则由对方控制，我方只能通过口径校验与探针验证。

# 关键属性

| 属性 | 说明 |
| --- | --- |
| 品牌映射 | **写死，只认 ZARA / HM / RL**；其它品牌走 default 分支——只打日志、返回 success、**不落库**（C1–C4 合并真根因） |
| 失败语义 | 业务失败仍返回 **HTTP 200**，body `code=400` → 我方记「成功」并 ACK → 数据静默丢失（C6） |
| 空 tags | `tags 为空 | code 200 | 无记录`：算一次「成功回调」但不落库（C6） |
| 租户判定 | 不由 key 决定：Secret 用 238 的 key，但 `brand=LOEWE` 被映射到 239（C4） |
| 我方成功口径 | **HTTP 2xx 且 `body.code ∈ {0, 200}`** |

# 被证伪的假设（C1–C6）

| # | 假设 | 结论 | 证据 |
| --- | --- | --- | --- |
| C1 | 商品必须存在才落库 | ❌ 排除 | 不存在的 spu 也能写入；在架真实商品反而不写 |
| C2 | `ety_ai_tagging_config.enabled=0` 是原因 | ❌ 排除 | 改 1 → 测 → 回滚 0，开关不是原因 |
| C3 | 字段没对齐导致不落库 | ❌ 证伪 | 同一份 9 标签载荷只把 brand 换成 ZARA → ✅ 写入 |
| C4 | 落库租户由 key 决定 | ❌ 错 | 238 的 key + `brand=LOEWE` → 239 |
| C5 | 本地 401「跑通了」 | ❌ 是失败 | 401 抛 `AmqpRejectAndDontRequeueException`，消息 reject 不重回队列 |
| C6 | 只判 `response.isOk()` 就是成功 | ❌ 假成功 | HTTP 200 + body `code=400` 仍被 ACK |

# 关系

- ↔ [[消息队列 / 阿里云 Serverless AMQP]]：假成功直接导致 ACK 后消息消失（配合无 DLX 即永久丢失）。
- ↔ [[静默失败]]：本实体是静默失败最重要的一类实例。
- ↔ [[打标评测方法论]]：采集成功判据必须排除这类「假成功」样本，否则坏数据混进分母抬高准确率（F1）。
