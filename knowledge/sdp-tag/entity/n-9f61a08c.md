> 生产商品打标主链路，以 scene → label 两阶段调用 judge 模型产出标签与分数。

# 定义

打标系统是正式的商品打标生产链路（代码名如 `tag.*`），负责接收商品与图谱快照，按语义组组织请求、调用 judge 模型、按阈值筛选出标签，并把结果落库与回调。

# 关键属性

- **两阶段流程**：`scene → label`。2026-10-26（`69f77f1`）删除了独立的维度阶段，见 [[取消维度阶段]]。
- **judge 模型可切换**：首个生产 judge 为 Ark 上的 doubao，2026-10-29 切换为 qwen3.8-flash，见 [[生产 judge 模型]]。
- **阈值**：全局 label 阈值首发 0.999，后改 0.9；分维阈值能力存在但默认不启用，见 [[分维阈值：能力而非默认]]。
- **结果语义**：`tag_product_label` = 最后一次成功结果 + `stale`。
- **只输出根标签**（本阶段刻意不做层级展开）。
- **证据存储**：gzip LONGBLOB，保留「最后一次成功 + 最近 3 次失败」。
- **重试分层**：批次级重试（网络/超时/5xx）+ 任务级重试（仅租约丢失/进程退出）。
- **配置版本**：额外记录 `rules_version`，因为「别名过滤」是代码而不是 `graphHash` 的一部分。
- **全量回刷**：进行前需确认数量/ token /费用（无硬预算）。Ark 侧估算约 2.7B 输入 token（26,990 件），证据约 38~43 GB 原始 / ~4 GB gzip，商品内并发 10。

## 子节：语义组划分与批处理

- 粒度三档：全场 / 每场景 / 每场景+维度，每个语义组**一个 JEV 请求**（删除 `tag.lab.batch-size=16`），见 [[一个语义组一个请求]]。
- 130 个维度中 90 个 >16 标签、16 个 >100、最大 314 标签——按题数拆批会大量浪费输入 token。
- **超限语义组仍需自动拆分**（10-26 `d504c9f`）：`LabBatchPlanner` 把超过 96k 上限的组切成**最少的连续子请求**。
  - 根因记录：314 题组失败**不是图片、不是标签备注**，而是 label v11 让每题约 341 字符，估算 81,317 token 超过 64k；早期「62k + 1.5k 图片」的猜测是错的。
- 成本优化主线：[[短题号别名]]（输入 −23.8% / 输出 −40.4%）。

## 子节：幂等与回调

- 幂等键用 [[解析后规范化内容摘要]]，`message_digest` 恒为首次报文摘要。
- 打标与回调**解耦**，需显式触发，见 [[打标与回调解耦]]、[[重发/重放语义]]。
- 按 brand 路由回调 key，未知品牌跳过，见 [[按 brand 路由 key]]。

# 关系

- 调用 [[JEV 推理服务]]（64k/请求、32k/题限额驱动拆批策略）与 [[生产 judge 模型]]。
- 依赖 [[标签图谱]]（维度定义、标签备注、分维阈值）、[[提示词管理]]（`tag.lab.*` 固定四段结构）、[[TagTaskRunSpec]]（运行规格快照）、[[sys_config 配置中心]] 与 [[Secret]]（回调凭据）。
- 产出经 [[回调服务]] 外发；部署于 [[部署环境]]。
- 实验对照在 [[Lab 实验台]] 中进行，两者共享同一图谱快照。
- 架构定位见 [[应用层模块化单体、部署层云原生]]。
