> 镜像推送的瓶颈所在：实例侧约 0.2 MB/s、并行不叠加，宿主直推不可用，pod 中转是正确方案。

# Schema

- **kind**: external_system
- **职责**：存储与分发部署镜像的托管仓库；在部署链路中同时是**容量瓶颈**。

# Definition

ACR（容器镜像仓库）是镜像推送与拉取的终点。本项目的镜像发布链路被它卡住，最终结论是**宿主直推不可用，pod 中转是正确方案**。

# 关键属性（实测）

| 指标 | 观测值 |
| --- | --- |
| ACR 实例侧上传速率 | 约 **0.2 MB/s** |
| 并行上传 | **不叠加**（多流并发不提速） |
| 网络质量 | 0% 丢包、10 ms 延迟（即不是链路质量问题） |
| 对照链路 | `maven.aliyun.com` 可达 **12.5 MB/s**（证明宿主网络本身正常） |
| 结论 | **只有 ACR 实例慢**；宿主直推不可用，pod 中转可行 |

# 冲突与裁决

**A4：上传慢是代理问题还是实例配额？**

| 说法 | 来源 |
| --- | --- |
| 大层被 Docker Desktop 代理掐断（`192.168.65.1:3128 broken pipe`） | `[D]` |
| **不是代理**——切无代理同样失败；`maven.aliyun.com` 能跑 12.5 MB/s，只有 ACR 实例慢 | `[Z]` |

**裁决：两者都对，指不同现象，都保留。**

- `[D]` 记的是**代理链路的断连**（事实）——直推失败链路的一环：Docker Desktop 代理（`192.168.65.1:3128`）在推大层时 `broken pipe`。
- `[Z]` 测的是**ACR 实例侧的容量上限**（也是事实）。
- **合并结论**：宿主直推不可用，原因叠加；**pod 中转是正确方案**。

这是「同一件事的不同阶段」型冲突的典型——不是谁错了。见 [[时间线仲裁口径]]。

# Relationships

- [[kubectl 运维通道]] — 同属「宿主直推 / pod 中转」部署链路的两端：pod 中转依赖 `kubectl` 通道，而该通道的 `cp` 与 `exec` 能力直接决定中转方案的成本。
- 部署模型：镜像构建 → 推送（受阻） → 集群拉取。
