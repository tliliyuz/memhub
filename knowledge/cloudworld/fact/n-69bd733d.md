> 同一端口上通配地址的非独占绑定可与更具体的 loopback 绑定并存，但独占绑定（SO_EXCLUSIVEADDRUSE）或已被占用的 loopback 会导致绑定失败；Windows 上表现依机器而异。

# 定义

描述同一 TCP 端口被多个程序监听时的共存规则，用于解释 `8096` 端口冲突为何在不同机器上表现不同：

- `0.0.0.0:<port>` 的**非独占**绑定，允许另一个程序再绑定更具体的 `127.0.0.1:<port>`，两者并存；发往 loopback 的请求由**更具体的地址**优先应答。
- 若通配绑定启用了**独占**标志（`SO_EXCLUSIVEADDRUSE`），或其他进程已占住 `127.0.0.1:<port>`，则更具体地址的绑定失败（`os error 10013`）。

# 共存矩阵（8096 实测）

场景：第三方 docker 栈监听 `0.0.0.0:8096`，[[cloud-world relay]] 需监听 `127.0.0.1:8096`。

| 第三方的绑定方式 | 结果 |
| --- | --- |
| `0.0.0.0:8096` 非独占 | relay 的 `127.0.0.1:8096` 绑定成功，两者并存；loopback 请求由 relay 的 bridge 应答 |
| `0.0.0.0:8096` 独占（`SO_EXCLUSIVEADDRUSE`） | relay 绑定失败（`os error 10013`），进程起不来 |
| 已有进程占住 `127.0.0.1:8096` | relay 绑定失败，进程起不来 |

# Significance

- 解释了**同一冲突不同现象**：Windows 上「非独占通配绑定」与「独占绑定」行为不同，不能凭一次现象推广结论。
- 界定了冲突是否致命的判据：不看「端口是否被监听」，而看**对方的独占性与具体地址**。
- 与 [[绑定失败即整体失败]] 结合，得出「共存成功 → 系统正常；共存失败 → 完全不可用」的二值后果。

# 约束条件

- bridge 必须绑定 **loopback** 地址（`crates/core/src/config.rs`），这是「与通配绑定并存」得以成立的前提；若改为通配绑定则失去该优势。
- `DEFAULT_BRIDGE_PORT = 8096`、`DEFAULT_RELAY_PORT = 8787`；bridge 端口**不得与 relay 端口相同**。
- 冲突纯属本机端口撞车，与服务端配方 `injection.externalGatewayUrl`（指向服务器自身 loopback）无关。
