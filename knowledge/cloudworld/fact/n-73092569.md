> 命名决策记录：产品工程名选定 cloud-world、否决 Nature-reawakens，并给出命名判据、派生标识清单、代价取舍与发布前验证项。

# 结论

产品命名用 `cloud-world`。`Nature-reawakens`（自然复苏）语义与产品功能无关，只适合当版本代号或界面主题名，不要占用工程命名。

该决策由 [[产品命名判据]] 得出，其直接产物是 [[标识同构派生]] 所要求的五类标识一致清单，覆盖 [[memhub]]、[[magpie]] 及后续接入服务。

# 判据

| 维度 | cloud-world | Nature-reawakens |
| --- | --- | --- |
| 是否描述产品 | 覆盖 [[memhub]]、[[magpie]] 及后续接入的服务 | 语义指向与功能无关，像游戏/小说名 |
| 命名可推导 | 仓库 / crate / bin / 配置目录 / 凭据条目都能同构派生 | 派生出来全是长串，CLI 天天敲，易拼错大小写和连字符 |
| 可检索性 | 看到名字就知道做什么 | 需要额外解释 |

判据的三个维度分别落到概念页 [[产品命名判据]]、[[标识同构派生]] 与 [[工程名与代号分离]] 上。

# 从名字派生出的全部标识（必须一致）

```
仓库          cloud-world
crate         cloud-world-core / -api / -relay / -service / -cli / -desktop
二进制        cloud-world（CLI）、cloud-world-desktop
配置目录      %APPDATA%\cloud-world
凭据条目      cloud-world / <profile>:panel-user-key
```

派生不了一致的名字，就会在各个层出现命名漂移，后期迁移成本远大于命名收益 —— 见 [[命名漂移与迁移成本]]。

六个 crate（`cloud-world-core / -api / -relay / -service / -cli / -desktop`）、配置目录 `%APPDATA%\cloud-world`、凭据条目 `cloud-world / <profile>:panel-user-key` 均无独立于父级命名规范的语义，故不单独建页，统一登记在 [[cloud-world]] 的派生标识清单内。

其中 `<profile>` 目前仅是凭据条目的一个路径片段；若后续出现权限 / 凭据模型文档，应升级为独立概念页（权限 / 凭据模型）并从 [[cloud-world]] 迁出。

# 代价与被接受的取舍

`cloud-world` 偏通用，GitHub 重名概率不低。处理办法：保留它作产品名，**仓库名加组织/用户前缀**（如 `<org>/cloud-world`），而不是换一个描述性更差的名字。这体现了一个通用的取舍原则：面对通用名，应通过命名空间（组织前缀）消歧，而不是牺牲描述性。

# 被否决的方案：Nature-reawakens

- 语义与产品功能无关，像游戏 / 小说名 —— 违反"是否描述产品"维度。
- 派生形式全是长串；CLI 日常高频输入，`Nature-reawakens` 易拼错大小写与连字符 —— 违反"命名可推导"维度。
- 可检索性差，看到名字无法判断用途，需要额外解释。
- 实操细节：若真要用在 GitHub 仓库名上，必须写成小写连字符 `nature-reawakens`，实际显示不会是大写形式。这本身也说明它不适合做工程标识。

保留用途：版本代号、界面主题名（属于与工程标识不同的命名空间，见 [[工程名与代号分离]]）。若后续出现多个落选候选，可抽为 comparison 页。

# 发布前验证

`crates.io` 搜索无同名 crate **不等于未占用**。正式发布前必须用 `cargo publish --dry-run` 验证。该检查项挂在 [[cloud-world]] 的 crate 标识派生流程上，与 [[标识同构派生]] 的 crate 层直接相关。
