> 未完成 ICP 备案的域名在边缘网络被按域名（SNI 层）阻断 HTTPS 的机制，可解释「间歇可开、样式全丢」的表现。

# 定义

备案拦截指：域名在**未完成 ICP 备案**的情况下，其 HTTPS 访问在部分网络的边缘节点被按域名阻断。由于阻断依赖握手阶段明文的 SNI（或 HTTP 层的 `Host`），表现为同机同路径下「带 SNI 死、不带 SNI 活」的分叉，见 [[SNI 分叉判据]]。

它是本次 [[memhub.work]] 握手重置故障的**根因**，而不是客户端、代理、服务端或证书问题。

# 显著性

- 决定了一整类故障的归因方向：任何在「应用层 / 代理层 / 证书层」的修复尝试都无效。
- 决定了方案分级：本地层规避只能算过渡，见 [[SSH 隧道过渡方案]]；根治只有完成备案或换已备案域名。
- 影响对外可用性模型的确定性：可达性随出口与时刻变化，不是稳定可预期的部署状态。

# 表现机理：间歇性可用与资源加载失败

「浏览器偶尔能开、偶尔样式全丢」由连接粒度的随机性解释，不是前端 bug，也不是缓存问题：

- HTML 主文档请求的某条连接侥幸通过 → 页面骨架渲染出来；
- 随后并行发起的 CSS / JS 连接被重置 → 样式全丢；
- 能否打开取决于**那一瞬间的连接是否经过被拦截的路径**，因此「刷新几次就好了」与「清缓存没用」会同时成立。

推论：用「页面能不能打开」判断服务健康在此类故障下不可靠，应改用 [[SNI 分叉判据]] 的对照方法。

# 为何代理绕不过

[[Clash]] 访问 [[memhub.work]] 命中 `GEOIP,CN,DIRECT`，代理与直连是**同一条出口**，因此经代理访问 5 次同样失败。给代理加 `DOMAIN-SUFFIX` 强制走境外节点可能避开某些出口的拦截，但多地区探测显示**并非所有出口都通**，不能作为稳定方案。

根本原因：拦截依据是域名（SNI），只要该域名仍处于未备案状态，换出口只在概率上变化成功率，不消除拒绝逻辑。

# Examples / 证据

- **腾讯云备案拦截页（直接证据）**：多地区 HTTP 探测中，部分节点返回 302 跳转至
  `dnspod.qcloud.com/static/webblock.html?d=...`
  —— 该落地页是备案拦截机制对外暴露的直接产物。
- **地区分布差异**：部分地区带 SNI 请求全部 reset，个别地区返回 200，说明拦截按边缘节点生效而非全局生效。
- **服务端对照**：从服务器自身及另一地区服务器直连该 IP，各种 SNI 全部握手成功 → 服务端不做 SNI 拒绝，排除服务端策略。

# 长期路径与退出条件

| 路径 | 说明 |
| --- | --- |
| 完成 ICP 备案 | 消除根因，恢复正常域名访问 |
| 换已备案域名 | 以具备备案状态的域名替换 [[memhub.work]] |

在上述任一条件达成前，任何本地 / 代理层规避都不构成修复，见 [[SSH 隧道过渡方案]]。
