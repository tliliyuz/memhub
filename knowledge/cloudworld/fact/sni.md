> 判断域名是否在「能看到域名的位置」被拦截的核心方法——同一路径下带 SNI 死、不带 SNI 活，即指向 SNI 层拦截。

# 定义

SNI 分叉判据是一种 TLS 层故障定位方法：在**出问题的同一条路径上**同时发起两组请求——一组携带 SNI（正常域名访问），一组不携带 SNI（IP 直连 + `Host:` 头）。若「带 SNI 死、不带 SNI 活」，则拒绝发生在**能够看到域名的位置**（SNI 是明文传输），而非证书链或服务端配置。

判据的核心在于**不看「能不能打开」，而看结果是否分叉**：单次「打不开」无法区分网络、证书、服务端还是拦截；而同一时刻同路径下的对照结果分叉，能唯一收敛到 SNI 层。

# 判据 Schema

| 请求 | 期望结果（正常情况） | 异常结果 → 推论 |
| --- | --- | --- |
| 明文 HTTP :80 | 真实服务端响应（如 301 跳转） | 若失败 → 网络通路本身有问题 |
| HTTPS **带 SNI** | TLS 握手成功 | 握手被重置 → 拒绝发生在可见域名处 |
| HTTPS **不带 SNI**（IP 直连 + `Host:`） | 握手成功、证书 CN 正确 | 若同样失败 → 证书或服务端配置有问题 |
| 经本地代理再访问同域名 | 与直连同结果（若共用出口） | 同样失败 → 代理未改变出口，无规避效果 |

判别逻辑：
- 带 SNI 失败 + 不带 SNI 成功 → **SNI 层拦截**（对外部按域名实施的阻断）。
- 带 SNI 与不带 SNI 同时失败 → 证书链或服务端配置问题，与域名拦截无关。
- 明文 :80 也失败 → 网络通路问题，判据不适用。

# Examples

本次在 [[memhub.work]] 上的实际四组结果：

| 请求 | 结果 |
| --- | --- |
| 明文 HTTP :80 | 正常 301，真实 nginx 响应 |
| HTTPS 带 SNI（`memhub.work`） | 连续 20 次全部握手被重置 |
| HTTPS 不带 SNI（IP 直连 + `Host:` 头） | 200，证书 `CN=memhub.work` 正常 |
| 经本地代理再访问同域名 | 5 次同样失败 |

结论：证书与 [[Nginx]] 都是好的，拒绝发生在能看到域名的位置，根因为 [[备案拦截（ICP 备案未完成阻断）]]。

# 配套的排除清单

判据给出结论后，仍需用分层排除法把其余层逐一钉死。本次实际验证过的假设与排除依据：

| 假设 | 排除依据 |
| --- | --- |
| [[Clash]] 坏了 | 经同一代理访问其他域名正常；该域名命中 `GEOIP,CN,DIRECT`，代理和直连是同一条出口 |
| 服务端 [[Nginx]] / 证书错 | 不带 SNI 直连返回 200 且证书 CN 正确；服务端自访问全通 |
| 换证书能解决 | 拦截发生在 SNI 层，与证书无关；DNS-01 换证书无效 |
| 客户端代码问题 | 三种客户端（curl / reqwest / 浏览器）复现一致 |
