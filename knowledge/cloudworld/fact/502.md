> 三条 SSH 隧道（8443 TLS / 8097 / 8445 明文）分工不同，-C 只对明文有效；502 SendRequest 有两种成因——隧道被拆或下游认证超时中断，401 与 502 可能同源。

# 定义

CloudWorld 客户端用三条独立 SSH 隧道把本地端口映射到同一台服务器，每条承担不同性质的数据。定位 `502` 必须先分清**是哪一段失败**，不能一律归因于隧道。

# 三条隧道的分工

| 隧道 | 本地端口 | 远端目标 | 内层协议 | 压缩 |
|---|---|---|---|---|
| data | 8443 | `127.0.0.1:443` | TLS（nginx） | 不加 `-C` |
| bridge | 8097 | `127.0.0.1:8096` | 明文 HTTP（tdai-proxy） | `-C` |
| gateway | 8445 | `127.0.0.1:8096` | 明文 HTTP（tdai-proxy） | `-C` |

[[本地 relay]] 的 `data_plane_url` 指向 `http://127.0.0.1:8445/claude-code/default`，即 [[真实请求链路]] 的第一跳。

# `-C` 只对明文有效（实测）

同样的服务器、同样的链路：

- 1 MB 随机数据过 TLS 隧道：不加 `-C` 3.43s，加 `-C` **4.17s（更慢）** —— TLS 密文不可压缩，压缩只白烧 CPU
- 413 KB JSON 过 TLS 隧道：1.70s → 0.70s（JSON 在 TLS 内层不可见，收益来自别处，不可依赖）
- 424 KB 真实 JSON 走明文 HTTP + `-C`：**16.2s → 1.86s**

结论：**内层是 TLS 就别加 `-C`；内层是明文 JSON 才加。**

# `502 error sending request` 的两种真实成因

报错形态：

```
502 upstream request failed: error sending request for url (http://127.0.0.1:8445/...)
    : client error (SendRequest)
```

`SendRequest` 是发送/连接阶段失败（连接被拒或被 RST），**不是上游返回的错误码**，请求没有走完。实测踩到两种成因：

## 成因一：隧道在传输途中被看门狗拆掉

`stopped tunnel 'gateway' ssh` → 在途连接被掐 → relay 报 502。判据：`watchdog.log` 是否有 `rebuilding` / `stopped tunnel`，与 502 时间是否对齐。成因与修法见 [[看门狗单实例互斥]]。

## 成因二：下游主动中断，与隧道无关

`tdai-proxy` 在做认证校验时超时（`auth service timeout (5000ms)`），当场中断 pipeline：

- 请求体**已传完** → 干净返回 `401`
- 请求体**还在传** → 连接被 RST → relay 报 `502`

所以 **401 和 502 可能是同一个根因的两种表现**，取决于放弃那一刻请求体传到哪儿。此时代谢掉的隧道与它无关，真正的病根在服务端（见另一侧知识库的 skill worker 空转问题）。

# 判断隧道是否真的不稳

三条独立证据，任一即可排除隧道：

1. **压测期间 `ssh` 进程 PID 不变** —— 连发 6 次 300KB 请求，PID 全程未变即隧道稳定
2. **服务器 `sshd` 日志**：`Received disconnect ... 11: disconnected by user` 中的 `11` 是客户端主动断开（sshd 的 `SSH2_DISCONNECT_BY_APPLICATION`），不是网络掉线
3. **探针退出码**：curl `exit=28` 是超时、`exit=56` 是接收数据失败；`code=000` 只说明没拿到 HTTP 状态码

# 探针与在途请求的冲突

健康探针走的是同一条 SSH 连接（所有 `-L` 转发复用同一个 SSH transport），大请求上传时会**队头阻塞**探针：

- 实测 `/health` 在负载中出现 `0.11s / 6.4s / 14.6s` 的巨大抖动
- 探针超时 → 看门狗误判 → 重建隧道 → 杀掉在途请求

因此看门狗必须遵守：**探针失败但端口上仍有 ESTABLISHED 连接时，跳过重建**。修复后日志形态应是 `probe failed` → `recovered`，不出现 `rebuilding`。

# 本地环境的 MTU 约束

- WLAN `NlMtu=1400`（persistent）
- 不分片探测：payload 1372（总 1400）通、1400（总 1428）丢
- **注意**：MTU 已设 1400 时用 `ping -f -l 1400` 测试必然 100% 丢包（总长会超），必须用 ≤1372 验证，否则会误判成链路故障

# 隧道覆盖缺口

`8424`（知识 API）与 `8125`（memory-hub 面板）属于 tdai-memory-hub，**不在看门狗管理的三条隧道内**。缺这两条时，依赖它们的客户端（如 team_brain MCP 的 `KNOWLEDGE_API_URL=http://127.0.0.1:8424`）会报 `fetch failed`，而链路本身完全正常。
