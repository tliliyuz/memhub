> memhub 云端面板 API 的三种响应形状、无效 key 语义分裂、身份参数载体约束与资产分页上限的实测踩坑记录。

# 来源信息

- **文档类型**：实测结论 / 踩坑记录（非需求、非架构、非会议、非 RFC）
- **主题**：[[memhub 云端面板 API]] 的真实调用形态
- **核心结论**：面板 API 不能统一解析——同一套 API 存在三种响应形状，必须按端点分别处理；更关键的是「无效 key」在不同端点上的表现不同（`200 + valid=false` 对 `401 code=401`），若把它当成统一的鉴权失败会写错错误分支。

# 摘要

本文以实测方式梳理了 [[memhub 云端面板 API]] 四类端点的调用形态，并给出若干反直觉的陷阱：

1. **响应形状三分法**：裸 JSON、`{code,message,request_id,data}` 信封、裸扁平 JSON 并存，见 [[响应形状三分法]]、[[信封响应格式]]。
2. **无效凭据语义分裂**：`auth/verify` 的无效 key 是「校验结果为否」的成功响应，`meta/{action}` 的无效 key 是 401 错误，见 [[无效凭据语义分裂]]。
3. **身份必须进 body**：仅带 `x-tdai-user-key` header 会被拒（400），见 [[身份参数载体约束]]。
4. **参数错误 ≠ 权限错误**：`UNKNOWN_META_ACTION` / `MISSING_TEAM_ID` / limit 上限 / 401 各有独立含义，见 [[错误码判定表]]。
5. **租户双维度**：`x-tdai-service-id`（租户）与 `team_id`（团队）正交，缺一不可，见 [[租户双维度模型]]。
6. **资产不是只有 wiki**：`limit` 上限 100，`data.total` 为总数、`data.items` 为当页，见 [[资产分类与分页模型]]。

# 四种端点的形状

| 端点 | 形状 | 无效 key 表现 |
| --- | --- | --- |
| `GET /api/v1/meta/instances` | 裸 JSON，无鉴权 | 不涉及 |
| `POST /api/v1/meta/auth/verify` | 信封 `{code,message,request_id,data}`，`data` 嵌套 `{valid,user}` | **HTTP 200 + code=0 + valid=false** |
| `POST /api/v1/meta/asset/list-accessible` 等 `meta/{action}` | 信封，`data` 形状按 action 各自不同 | **HTTP 401 + code=401** |
| `POST /api/v1/auth/user-key/login` | 裸扁平 JSON，**不套信封** | 未知 key 会自动注册，仅在明确同意后调用 |

对应页面：[[meta-instances 端点]]、[[meta-auth-verify 端点]]、[[meta-action 端点族]]、[[auth-user-key-login 端点]]。

# 陷阱清单

- `auth/verify` 的无效 key 不是错误，而是一次成功的「校验结果为否」；客户端必须以 `valid` 布尔值分支，不能按 HTTP 状态码判定。
- `user_key` 必须进请求 body（`auth/verify` 读 body；`asset/list-accessible` 接受 `user_key` 或 `user_id` 二选一）。header 不满足身份要求。
- 不要把 key 放进命令行参数（进程列表可见），见 [[凭据安全处理实践]]。
- `user-key/login` 对未知 key 自动建号，属有副作用的调用，见 [[自动注册语义]]。
