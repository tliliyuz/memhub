> 记录 memhub.work 的 HTTPS 在部分网络下 TLS 握手被重置的归因过程，结论为域名 ICP 备案未完成导致的边缘网络拦截，并给出 SSH 隧道过渡方案与两条长期路径。

# 文档摘要

本文档记录 [[memhub.work]] 的 HTTPS 从部分网络访问时 TLS 握手被重置的故障归因过程。结论是：**不是客户端或证书问题，而是域名备案未完成导致的边缘网络拦截**。文档性质为「归因结论 + 方案取舍记录」，产出了可复用的排障判据 [[SNI 分叉判据]]，并明确了过渡方案与长期路径的分级。

# 核心结论

- 不是 [[Clash]] 配置错、不是服务端 [[Nginx]] / 证书错，**换证书也解决不了**。
- 根因是域名备案未完成被边缘网络拦截，见 [[备案拦截（ICP 备案未完成阻断）]]。
- 判断依据不看「能不能打开」，看**同一台机器上带 SNI 与不带 SNI 的结果是否分叉**，见 [[SNI 分叉判据]]。

# 诊断判据：SNI 分叉

在出问题的那条路径上同时打两组请求：

| 请求 | 结果 | 说明 |
| --- | --- | --- |
| 明文 HTTP :80 | 正常 301，真实 nginx 响应 | 网络通路本身没问题 |
| HTTPS **带 SNI**（`memhub.work`） | 连续 20 次全部握手被重置 | 只有 TLS 握手这一步被掐 |
| HTTPS **不带 SNI**（IP 直连 + `Host:` 头） | 200，证书 `CN=memhub.work` 正常 | 证书与 nginx 都是好的 |
| 经本地代理再访问同域名 | 5 次同样失败 | 代理没有改变出口 |

**关键推论**：带 SNI 死、不带 SNI 活，说明拒绝发生在**能看到域名的位置**（SNI 是明文），而不是证书链或服务端配置。若服务端证书有问题，不带 SNI 也一样失败。

# 为什么「浏览器偶尔能开、偶尔样式全丢」

这不是前端 bug，也不是缓存问题。HTML 请求的某条连接侥幸通过 → 页面骨架渲染出来；随后并行发起的 CSS/JS 连接被重置 → 样式全丢。**能否打开取决于那一瞬间的连接是否经过被拦截的路径**。所以「刷新几次就好了」和「清缓存没用」会同时成立。详见 [[备案拦截（ICP 备案未完成阻断）]] 的表现机理小节。

# 归因用的外部证据

- 同域名从服务器自身、以及另一地区的服务器直连该 IP，各种 SNI 全部握手成功 → **服务端不做 SNI 拒绝**。
- 多地区探测：部分地区全部 reset、个别地区 200；部分 HTTP 探测节点返回 302 到 `dnspod.qcloud.com/static/webblock.html?d=...` —— **腾讯云备案拦截页**这一条是直接证据。

# 被排除的假设（都实际验证过）

| 假设 | 排除依据 |
| --- | --- |
| Clash 坏了 | 经同一代理访问其他域名正常；该域名命中 `GEOIP,CN,DIRECT`，代理和直连是同一条出口 |
| 服务端 nginx / 证书错 | 不带 SNI 直连返回 200 且证书 CN 正确；服务端自访问全通 |
| 换证书能解决 | 拦截发生在 SNI 层，与证书无关；DNS-01 换证书无效 |
| 客户端代码问题 | 三种客户端（curl / reqwest / 浏览器）复现一致 |

# 过渡解法与代价

- 过渡期用 SSH 隧道把 `127.0.0.1:8443 → 服务器:443`，客户端改走 loopback。**这是过渡方案不是修复**，依赖本机隧道存活，需要 watchdog 维持。见 [[SSH 隧道过渡方案]]。
- 长期只有两条路：完成 ICP 备案，或换已备案域名。
- 给本地代理加 `DOMAIN-SUFFIX` 强制走境外节点可能避开某些出口的拦截，但多地区 reset 说明**不是所有出口都通**，不能作为稳定方案。
