> B 机三容器由 systemd oneshot 单元拉起，每次启动都重建容器，因此运行期手工改动不可持久；服务器 A 的原生 systemd 进程则是语义相反的反例。

# 容器化部署与重建语义

## 定义

记忆栈采用"**声明式脚本 + oneshot 拉起**"的最小容器编排模型：没有 compose/k8s，`[[memhub-stack 服务单元]]`（`memhub-stack.service`，oneshot）执行 `/opt/memhub` 下的启动脚本，按 `core → hub → proxy` 顺序创建/重建三个 [[Docker]] 容器。

更一般地说，容器化部署与重建语义指：当容器由 systemd（`memhub-stack.service`，oneshot）在每次启动时**重新创建**，容器内文件系统与运行期手工改动都随重建丢失。因此所有配置必须固化进启动脚本或挂载卷，否则「改了就没了」。

## 关键推论

1. **重建即覆盖**：任何 `docker update`、`docker exec` 级别的手工改动，在下一次 `systemctl start memhub-stack` 后消失。
2. **配置的唯一真实来源是启动脚本**（以及 `.env`）。例如内存上限若要生效，必须写进脚本中的 `docker run --memory=...`。
3. **状态与配置分离**：需长期保留的数据只能放在卷里（见 [[Docker 卷数据持久化]]），容器自身视为无状态、一次性的。
4. **启动顺序即依赖顺序**：core 先于 hub，hub 先于 proxy。

## Schema

| 维度 | 容器化（[[腾讯云 CVM VM-0-10-ubuntu]]，B 机） | 原生进程（[[服务器 A（instance-47g8z54m）]]，A 机） |
|---|---|---|
| 运行时 | [[Docker]] 27.5.1 | 无 Docker |
| 编排 | [[memhub-stack 服务单元]]（systemd oneshot） | `clickhouse-server.service` |
| 启动顺序 | core → hub → proxy | 单进程 |
| 运行期改动 | **不可持久**（重建即丢失） | **可持久**（写盘即生效并保留） |
| 持久化数据 | 需 Docker 卷（[[Docker 卷数据持久化]]） | 直接落系统盘（40 GiB，已用 48%） |
| 配置来源 | 必须固化进启动脚本 | `/etc/clickhouse-server/` 等常规配置文件 |

## 示例

- B 机：`memhub-stack.service` 每次启动都重建三个容器，改容器内的 nginx.conf 或环境变量必须在启动脚本里同步修改，否则重启即回滚。
- A 机（**反例**）：[[ClickHouse]] 是 systemd 原生进程，手工修改配置文件后重启服务即可长期生效，无需重建；但反过来，这也意味着**缺少「声明式重建」带来的可复现性**——主机上不存在「用脚本重建出相同状态」的保证。

## 意义

- 让"改了什么"可审计、可复现，避免配置漂移（configuration drift）。
- 是待办 1（内存 limit）能否真正落地的**根因约束**：只在运行期设 limit 等于没设。
- 排障时必须先判断该主机属于哪种语义，否则「改了没生效」与「改了但被回滚」会混淆。
- [[magpie gateway]] 迁移到 B 机后仍是**宿主机原生进程**，不受容器重建影响——一台主机上可同时存在两种语义，按进程而非按主机区分。
- 备份策略随之不同：B 机依赖 Docker 卷，A 机依赖系统盘/文件级备份。
