> 客户端 → 8096 Memory Proxy（记忆注入/L0 落库）→ 3425 Magpie（模型路由/额度）→ 各家上游的串联拓扑；就模型调用链路而言 Proxy 必须在最外层，MCP 检索链与之平行、不经过 8096。

# 定义

级联代理拓扑指把两个网关**串联**起来，让「记忆能力」与「模型自由度」同时可得。模型调用路径是一条严格串联的分层链：

```
DSH / Codex / Claude Code
        │  选任意模型
        ▼
  8096  Memory Proxy   ←── 记忆注入(L2/L3) + L0 落库 + L1 召回 发生在这里
        │
        ▼
  3425  Magpie         ←── 只做模型路由 / 兜底 / 计价 / 额度
        │
        ▼
  applesay / gpt / workbuddy / trae-cn / qoder-cn ...
```

每一层职责单一：Proxy 管记忆，[[Magpie]] 管模型选择与成本，上游只负责推理。客户端只面向 Proxy（或 Magpie），不直连上游，凭据因此可留在服务端（见 [[凭据分层模型]]）。

**分层顺序原则：[[Memory Proxy]] 必须在最外层。** 顺序不可调换，否则记忆注入与 L0 落库会缺失——记忆注入与落库要看到完整的请求与响应。该原则在**模型调用链路**语义下成立；读取团队资产的检索链另有独立通道，见下文「与检索链的关系」。

# 显著性

原始状态下客户端只能二选一：

| 选的 provider | 结果 |
|---|---|
| Memory Hub（8096） | 有记忆，但只有 deepseek 系列模型（Magpie 的子集） |
| Magpie（3425） | 模型丰富，但绕开 8096，**记忆不会被记录** |

级联把这个二选一变成「两者兼得」。落地后 DSH 可选模型从 2 个增至 66 个，注入管线 `errorCount=0`，各 provider 模型均 200。

此外，分层带来的直接收益包括：

- 每一层职责单一：Proxy 管记忆，[[Magpie]] 管模型选择与成本，上游只负责推理。
- 客户端只面向 Proxy（或 Magpie），不直连上游，凭据因此可留在服务端（见 [[凭据分层模型]]）。
- 故障分段定位依赖这一顺序（见 [[Proxy 转发故障分段定位]]）。

分层顺序决定了「哪一层负责什么」：记忆层不碰模型选择，模型层不碰记忆。

# 排序原则的两条独立理由

1. **记忆归属**（本页）——Proxy 需要看到**客户端原始请求**才能注入上下文、把对话归档成 L0；若放在内层，Magpie 已改写过的请求会让记忆归属失真。
2. **凭据归属**（[[凭据分层模型]]）——[[Magpie]] 是密钥替换型网关，反向串联必然 401 `invalid user_key`；只有 `sk-mem-` 用户密钥能进 8096。

两条理由各自独立成立，任一都足以否决「把 Memory Proxy 注册成 Magpie 的 provider」。

# 五步验证顺序

拓扑正确性按「从外到内」逐段收敛，任何一项不过则链路不完整：

1. **上游是否正确** —— 读 `docker exec tdai-proxy head -12 /data/config.yaml` 的 `upstream.url`。
2. **容器到 Magpie 是否通** —— 容器内 `curl http://host.docker.internal:3425/` 期望 200。
3. **模型穿透** —— 对 8096 发一次最小 `chat/completions`，期望 200；502 看挂载/上游段，503 `No available channel` 说明上游没改成功。
4. **注入管线在跑** —— 日志 `injection.pipeline.done` 且 `errorCount=0`。
5. **记忆计数在涨** —— 面板 `chat-memory/layer` 查 L0/L1 的 `total` 增长。

这套顺序本身就是一种故障分段方法，与 [[Proxy 转发故障分段定位]] 互为补充。

# 与检索链的关系（2026-11-10 补充）

本拓扑**只描述模型链路**。[[Team Brain MCP]] 的只读检索是**另一条平行路径**，MCP 本身**不参与模型转发**：

```
Agent -> team-brain-mcp (stdio) -> { Knowledge 8424 | Panel 8125 } -> Memory Core 8420
```

细分到端点：

```
Agent ──MCP(stdio)──> Knowledge 8424（/v3 免密钥）
                   └─> Panel 8125（/api/v1 + sk-mem）
                            └─> Memory Core 8420
```

两个关键推论：

1. 检索链**不经过 8096**：`memory-bridge` / `skill-bridge` 因会话耦合（`40101 session not initialized`）被 MCP 弃用，改走面板与 Knowledge（见 [[MCP 双后端只读接入]]）。因此 [[Memory Proxy]] 的 `bridge` 端点与 MCP 无关，其 `40101` 也解释了为什么 MCP 只能走面板 API。
2. MCP 可用性**不影响**模型调用链路，反之亦然；但两者共享 [[Memory Hub]] / [[Memory Core]] 的下层，底层故障会同时波及。

综上，「Proxy 是必经点」只在**模型调用**语义下成立；读取团队资产有独立通道。
