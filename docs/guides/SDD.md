# SDD — 规范驱动开发

| 适用范围 | 通用开发流程：从 ADR 检查到规格、验收测试与最小实现的约束 |
| 不负责 | 各仓的命令与目录；见 [DEVELOPMENT](DEVELOPMENT.md)。文档归属与裁决见 [DOCUMENT_GOVERNANCE](DOCUMENT_GOVERNANCE.md) |

本文件是入口「核心规范」的全文。任何业务行为先由可审查的规范定义，再由测试转成
可执行验收条件，最后才写生产实现；入口只保留一句门禁，不承载流程细节。

## 1. 流程

```text
ADR 检查与裁决
  → 规格确认
  → 验收条件与测试场景
  → RED：先写测试并确认因目标行为缺失而失败
  → GREEN：编写使测试通过的最小实现
  → REFACTOR：在持续绿灯下整理设计
  → 受影响模块完整验证
  → 权威文档与变更记录同步
```

## 2. 强制规则

- 没有明确规格，不写测试和生产代码；没有从规格导出的验收测试，不写生产代码。
- 没有亲自观察到正确的 RED，不进入 GREEN；RED 若源于语法、Fixture、环境或 Mock 错误，先修正测试，不得据此进入实现。
- GREEN 只实现当前验收条件要求的最小行为；相关测试全部通过后才允许重构。
- 不得根据既有实现反向编写规范或测试；实现领先于规范时先补裁决，不改规范迁就代码。
- 新功能、Bug 修复、行为变更和架构调整先按 [ADR 治理规则](../decisions/README.md) 执行检查；命中时在解除门禁前不继续规格、测试或实现。
- 规范缺失、冲突或无法导出验收条件时暂停实现，按
  [DOCUMENT_GOVERNANCE](DOCUMENT_GOVERNANCE.md) §5、§6 完成取证、分类与裁决。
- 完成声明必须附本次实际执行的验证命令和结果；未执行的内容不得写成通过。

## 3. 例外与验证

- 无法制造业务 RED 的纯文档、注释、生成物或配置变更，说明例外理由并执行适用的格式、链接、键集或 smoke 验证。
- 例外只免除测试先行，不免除验证记录；例外理由写入完成声明或提交信息。
- 受影响模块的定义与验证命令由各仓 [DEVELOPMENT](DEVELOPMENT.md) 的验证矩阵给出。

## 4. 与文档治理的关系

SDD 产出的规格、验收条件与实现证据是文档治理的输入：规范进权威文档，实施历史进
ADR 与 CHANGELOG，讨论过程不进入规范正文。两者的裁决顺序与冲突分类以
[DOCUMENT_GOVERNANCE](DOCUMENT_GOVERNANCE.md) 为准。
## 5. 交付物分档与计划文件

需求按「是否需要一次长期裁决」和「是否跨多批次」两维分三档，每档对应固定载体，避免
文档只增不减，也避免跨会话丢上下文：

| 档 | 触发条件 | 载体 | 是否写进 docs |
|---|---|---|---|
| 小 | 单批次、单会话可完成，无跨模块契约变更 | 会话 + 验收测试 + CHANGELOG | 否 |
| 中 | 够不到 ADR 触发，但跨多会话或多提交批次，或需移交给别的 agent | 仓外任务跟踪（任务系统、issue 或会话外记录）：范围、验收条件、批次清单与进度 | 否；仅当必须随仓库演进、跨会话可见时，才落 `docs/plans/spec/日期-名称-spec.md` |
| 大 | 命中 [ADR 触发清单](../decisions/README.md) | ADR 记录裁决；跨批次拆解可选 `docs/plans/spec/日期-名称-spec.md` | ADR 必写 |

- **升级**：中档需求中途出现需要长期裁决的岔路时，升级为 ADR；ADR 不因实现未完成而失效。
- **计划文件边界**：`docs/plans/` 下的计划只写批次划分、依赖、回滚与进度，只引用真源，
  **不得复述规范正文与验收条件**；它不是长期真源，结论仍要沉淀进权威文档。
- **roadmap 是理想排期**：`docs/plans/ROADMAP.md`（可选）只描述大致方向与阶段划分，
  不承诺时间、不作实现准入门槛；临时需求随时可插入，是否已实现以 CHANGELOG 为准，
  单次变更不要求回填 roadmap。
- **禁止**：任何档位都不把规范内容复制进计划文件；一旦出现复述，该部分应归入真源。
