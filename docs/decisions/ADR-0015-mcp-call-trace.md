# ADR-0015 MCP 调用轨迹落库，治理台可见

| 属性 | 值 |
|:---|:---|
| 状态 | proposed |
| 日期 | 2026-11-25 |

## 背景

MCP 检索组上线后，调用量一直没有可核对的数字。现有观测只有三处，都不够用：

- `tools.py` 里写工具的业务日志只覆盖写候选，读工具没有记录；
- nginx `access_log` 只记 `POST /mcp`，不知道调用的是哪个工具、用的哪份凭据；
- `kb_write_audit` 只记写路径，且语义是「写入审计」，不是「调用轨迹」。

同时客户端会把 MCP 工具的 schema 延迟下发（progressive disclosure），模型只看得到工具名，必须先 `ToolSearch` 才能拿到参数。这让「装了 MCP 却几乎不被调用」变成常见现象，而服务端无法区分「没人用」和「用了但失败」。没有按工具、按凭据、按结果分布的调用数据，任何关于工具描述或 instructions 的改动都无法验收。

## 决策

1. 在 `kb` schema 新增 `kb_mcp_trace` 表，由 MCP HTTP 入口（`McpEndpoint`）统一记录：
   - 每次 `tools/call`：请求 id、JSON-RPC id、凭据、工具、状态、错误码、耗时、结果大小；
   - 每次鉴权/路由拒绝（401/403/405/429）：同样落一行，`status=rejected`。
2. **只记元数据**：不记参数原文、不记正文、不记 token；参数只留规范化后的 sha256 摘要。
3. **凭据名可选**：`MEMHUB_MCP_GRANTS` 的每条 grant 增加可选 `name`；未配置时界面降级显示 `credential_id`（摘要前 12 位），不阻断启动。
4. **可靠落库**：独立事务写入；失败重试；仍失败则追加到本地 spool 文件，下次成功写入时补投。禁止静默丢弃。
5. **保留 30 天**：写入路径按小时节流执行一次过期清理，不新增定时器或独立进程。
6. 管理台「治理」菜单新增「调用轨迹」页，读 `GET /api/v1/kb/mcp-traces`。

## 备选与否决理由

- **只写结构化日志**：能查 grep 不能聚合，也无法在管理台按凭据/工具筛选，否决。
- **OpenTelemetry 导出**：需要额外后端；`stateless_http=True` 下客户端身份不随 `tools/call` 传递，关联成本高；作为后续可选补充保留，不作为本轮主路径。
- **解析客户端 transcript**：只能覆盖单机、单客户端（[CC]），覆盖不到 Codex 等其它 agent，也看不到鉴权拒绝，否决。
- **复用 `kb_write_audit`**：该表语义是「写入审计」，只覆盖写路径，混入读调用会污染既有审计口径，否决。
- **纯内存计数**：进程重启即丢，无法回答历史问题，否决。

## 后果

- 新增一张表与一个 Alembic 迁移；`kb` 运行角色需要该表的 `INSERT/SELECT/DELETE` 权限。
- 每次 MCP 请求多一次小事务写入；按当前调用量可忽略，但需观察 P99。
- spool 文件需要可写目录；`MEMHUB_DATA_DIR` 未配置且未显式给 `MEMHUB_KB_TRACE_SPOOL` 时，spool 退化为关闭并记 ERROR 日志——此时可靠性只剩「重试」，必须在部署检查中确认该路径可写。
- 30 天保留意味着历史趋势最多看一个月；需要更长周期时应先把数据聚合到日表，而不是延长明细保留。
