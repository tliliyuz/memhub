# ADR-0010 采集写的目标边界改为「显式 + 已登记 + 活动」

| 属性 | 值 |
|:---|:---|
| 状态 | accepted |
| 日期 | 2026-11-23 |

## 背景

ADR-0009 为采集写入引入设备—知识库授权文件，并在存储层保留了隐式建库。实际运行暴露两个问题：

1. 授权文件把运维成本转移给用户：每加一台设备或一个库都要上服务器改 JSON，文件缺失或格式错误还会让采集整体失败。
2. 存储层 `write()` / `append_edges()` 对父目录 `mkdir(parents=True)`，任何写路径（采集、worker、CLI）遇到不存在的库都会顺手建出来，入口校验之外没有第二道防线。

另一个契约问题：采集接口曾提供 `POST /ingest/projects` 代理建库，把「新建知识库」和「上传」混在客户端，削弱了「目录存在 ≠ 库登记」的判定。

## 决策

- 采集写入的目标边界统一为三条同时成立：显式 `project`（`^[a-z0-9][a-z0-9._-]{0,63}$`，保留 `auto` 不算显式，不做裁剪）、在 `.kbs.json` 严格登记、当前活动（`blocked/<id>` 不存在且是普通目录，不接受符号链接与重解析点）。设备 token 与设备注册仍是前一道鉴权，但注册设备或创建库都不授予写权限。
- 移除 `MEMHUB_INGEST_GRANTS_PATH` 与设备—知识库授权文件。单设备场景下，「已登记 + 活动」就是正确的最小写边界。
- 拒绝发生在配额、落盘和游标变更之前，统一返回业务码 `1003`，用 `data.reason` 区分 `missing` / `reserved` / `invalid` / `unregistered` / `inactive` / `target_conflict`；登记状态无法读取时返回可重试的 `500` / `2001`，不回显设备、项目值或路径。
- 存储层不再隐式建库：`KnowledgeStore.write()` / `append_edges()` 发现目标库目录不存在时抛 `ProjectMissing`，只对 `<project>/<kind>` 一级目录做非递归 `mkdir`；只有 `catalog.create_kb` 这条显式路径可以创建一级目录。
- 采集端只负责上传与只读列表：删除 `POST /ingest/projects`，建库只在管理台 `POST /api/v1/kb/projects`。`GET /ingest/projects` 保留，过滤条件改为「已登记且活动」，响应形状不变。
- worker 在调用模型前和写入锁内两次复核目标；期间被归档或从登记中移除的记录进入 `pending_review`，不重建目录、不改投。
- 每次采集写入一条结构化审计：设备、目标、接受/拒绝、理由、时间；不含正文与 token。

## 备选与否决理由

- 保留授权文件：运维成本高，文件本身成为单点（手误或缺失即整体拒绝），而单设备场景没有收益。
- 只在接口层校验、存储层继续隐式建库：入口之外的写路径（worker、CLI、脚本）仍能创造目录，事故根因没有被消除。
- 采集端保留「新建并上传」代理：把建库写权限暴露给客户端，且与「目录存在不等于登记」冲突。
- 未登记时自动建库并登记：目的地由客户端决定，和用户选择不一致时无法回滚。

## 后果

- 部署不再需要授权文件；升级须同次切换 ingest、worker 与 kb-api，旧版客户端调用已删除的建库代理会收到 404/405。
- 未登记或已归档的目标一律 400/1003；桌面端按 `data.reason` 分支提示，不自动重试。
- 目标是否存在通过 1003 的 `data.reason` 有一定可观察性，接受该取舍，范围限于已认证的注册设备。
- 审计当前只落应用日志，尚无可查询表；`created_by_device` 等扩展留待后续决策。
