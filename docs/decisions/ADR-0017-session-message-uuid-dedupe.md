# ADR-0017 会话去重单位改为消息 uuid，fork 不再重复抽取

| 属性 | 值 |
|:---|:---|
| 状态 | accepted |
| 日期 | 2026-11-26 |

## 背景

采集端（agent-console）对 Claude Code 的 `--fork-session` 会话会产生一个新的 `.jsonl` 文件，从 offset 0 全量上传；fork 点之前的每一条消息都在新文件里原样复制，只把每行的 `sessionId` 改写成新会话 id。2026-11-26 采集端实测：普通会话 31 行，fork 后新文件 36 行；两边 `uuid` 相同的消息 18 条，但没有一条字节相同（差异只有 `sessionId`，长度不变、偏移对齐），jsonl 里也没有 `forkedFrom*` 之类的行级标记。

服务端现有的两层身份都对不上这种复制：

- 切片级去重键是 `(source_id, 切片 sha256)`（`src/memhub/ingest/postgres.py` 的 `seen_shas`、`src/memhub/ingest/store.py` 的内存实现），raw 队列同样按 sha 内容寻址（`src/memhub/queue/rawstore.py`）。`sessionId` 一变，整片哈希全变，`duplicates=0`。
- 游标键是 `(device_id, source_id, path)`（`src/memhub/ingest/postgres.py`）。fork 是新路径，`from_offset=0` 合法，不会触发 `1004`。

worker 逐 raw 文件独立处理（`src/memhub/worker/daemon.py`），渲染时解析 JSONL 但不读消息 `uuid`（`src/memhub/worker/render.py`），跨文件没有任何消息级身份。后果是：fork 前的历史整段重传、重新落盘、重新跑 LLM 抽取；merge 是追加式，同 slug 同正文不重复追加，但抽取措辞不稳定，措辞不同就追加「## 补充（日期）」，slug 不同则是新节点，知识库里出现近似重复（`src/memhub/worker/merge.py`）。

定位结论：不是去重机制失效，而是**去重粒度选错了**——知识抽取的语义单位是「一条消息」，现有键是「一段字节切片」。fork 只是把「复制语义单位、改写字节」这个矛盾暴露出来。

不可在服务端挽回的部分：重传的带宽已经发生。服务端能省的只有磁盘、LLM 调用和知识重复，方案不承诺免去上传。

## 决策

1. **去重单位改为消息 `uuid`**：JSONL 会话行若带顶层 `uuid`，以它作为消息身份。fork 复制的消息保留原 `uuid`，是可靠信号。
2. **作用点在 worker 渲染/抽取之前**：`render_session_blocks` 解析阶段就把已见 `uuid` 的消息过滤掉，再进入分节、LLM 抽取与 merge。ingest 协议层不解析会话语义，raw 队列保持原样。
3. **索引键为 `(project, source_id, uuid)`**：同一项目内同一条消息只抽取一次；知识归属以 project 为准，目标重定向后可按需重新抽取，不与切片级 `seen_shas` 的 source 级口径强行统一。索引存放在运行态库（worker 已有 `MEMHUB_DB_URL`），表名与 DDL 待规格阶段定（候选 `seen_messages`），迁移按 `schema_migrations` 前向追加。
4. **记账时机**：只有抽取与 merge 成功后才写索引；抽取失败不记，保留 raw 文件等待重试，不丢证据。崩溃窗口内最多重复抽取一次，重复的内容仍受 merge 的同正文去重与 slug 合并约束。
5. **整片命中的快速路径**：一个 raw 文件里的可渲染消息全部命中索引时，跳过 LLM，直接标记已处理。
6. **raw_store 保持原样**：不因去重改写或丢弃收到的字节，`processed_raw` 仍保留原文供事后重跑抽取；重跑时如需重抽已见消息，必须显式清理对应索引（操作入口待规格阶段定）。
7. **客户端契约不改**：`ingest-api.md` 的 `sha256`、`duplicates`、批次幂等语义全部不变。消息级命中只体现在 worker 日志与指标，不进入采集返回值。客户端不需要识别 fork。
8. **无 `uuid` 的源不做消息级去重**：wiki、docs 与其它没有消息标识的 `sessions` 容器保持现有切片级去重，行为不变。
9. **重扫语义显式化**：`source_rev` 提升后的重扫只补尚未见过的消息，不自动重抽已见消息；这与现有 `seen_shas` 无重置机制的行为一致，但必须在契约与操作文档中写明，避免被当成「重扫 = 全量重抽」。

## 备选与否决理由

- **ingest 落盘前按 uuid 过滤消息**：能让 `duplicates` 直接反映消息级重复并省磁盘，但 raw_store 从此是派生视图，prompt 升级后无法重跑被过滤掉的原文；还要重新定义 `sha256`（原文哈希 vs 过滤后内容）与 `duplicates` 的契约语义，并处理切片落在半行上的缓冲。与「原始观测只进 raw_store」的定位冲突；否决作为第一期，保留为后续优化。
- **客户端识别 fork、不重传历史**：jsonl 无行级 fork 标记，只能靠 uuid 抽样比对与游标跳空，容易误伤普通续写；采集端自己也建议不做；否决。
- **切片哈希归一化后比对**（先剔除 `sessionId` 再算哈希）：父会话与 fork 的切片边界不同，且 fork 的同一片还包含新消息，整片仍对不上；要正确切分还是回到消息粒度；否决。
- **在 merge 层按节点正文去重**：merge 看不到消息身份，LLM 每次措辞不同，正文比对只能挡住完全相同的文本，挡不住近似重复；否决。
- **索引只按 `(source_id, uuid)`**：与 `seen_shas` 口径一致，但知识归属是 project；目标重定向到新库时会把历史错误地判为已见。代价只是索引多一个维度；否决。
- **按会话级 `forkedFromSessionId` 跳整文件**：只能覆盖「整文件都是复制」的情况，fork 之后恢复续写的增量仍要逐消息判断，且该标记不在行级、服务端拿不到；否决。

## 后果

- 新增运行态表、索引查询与批量写入、迁移脚本；worker 每片多一次索引读写，开销相对 LLM 调用可忽略。
- 上传带宽与 raw 磁盘占用不变：fork 仍会把历史整段传上来，直到 raw_store 配额或 `processed_raw` 保留期回收。这是本决策明确不解决的问题。
- `duplicates` 计数仍是切片级；采集端看到 `duplicates=0` 时，重复可能已在 worker 侧被消息级去重，需要看 worker 指标，不能只看采集返回值。
- 索引按消息增长（每源每项目一条消息一行），量级与历史消息数线性，可忽略；清理与归档入口随索引表规格一并定义。
- 先到者胜：同一 `uuid` 若在不同 fork 里内容不一致（预期不应发生），以先成功抽取的版本为准，后到版本跳过。
- 跨切片残行（一行被字节 offset 切成两片）在现有实现里本来就解析失败被跳过，消息级去重保持同一行为，不新增回归。
- 实施前仍需在规格阶段定：表名与字段、索引清理/重抽的操作入口、worker 指标字段、是否需要按源开关；ADR 只裁决方向与边界。
