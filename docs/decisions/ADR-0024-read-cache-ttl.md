# ADR-0024 读缓存 TTL 由 60s 提到 600s

| 属性 | 值 |
|:---|:---|
| 状态 | accepted |
| 日期 | 2026-11-29 |

## 背景

本 ADR 是 [ADR-0023](ADR-0023-kb-read-cache.md) 的参数修订：决策方向不变，只调整 TTL
取值。

线上实测（main `8707db3`）显示：热命中 `nodes` 10–12ms、`stats` / `audit` 7–8ms，而冷
路径 0.5–0.7s。管理台低频访问时，60s TTL 经常在两次操作之间把 key 全部过期——隔几分钟
再打开页面，第一次请求仍是冷路径，等于「每次都冷」。当前缓存只有 3–5 个 key、几百 KB，
按 `allkeys-lru` 512MB 的内存上限看，短 TTL 并不能省下任何有意义的内存。

## 决策

`DEFAULT_TTL_SECONDS` 由 60s 调整为 600s（10 分钟），其余口径不变：

- 正确性仍完全由 `cache_epoch()` 保证：节点或边任何增删改都换 epoch、旧 key 立即失联，
  TTL 只是内存背压上限；
- 缓存值仍带 `SCHEMA_VERSION`，版本不匹配即重算；
- 唯一的时间相关读是 `audit` 的「陈旧」判定（用检出时刻比较 `valid_until`），命中时最多
  滞后一个 TTL；管理台刷新时看到的是最近一次检出，10 分钟内的边界漂移接受；
- 若将来单 key 体积或 key 数显著增长、内存成为真实约束，再按命名空间拆 TTL；目前不拆。

## 备选与否决理由

- **保持 60s**：实现不动，但低频访问下命中率接近 0，缓存只对连续刷新有效。
- **300s**：比 60s 好，但隔一次会议或几分钟切页仍会过期；相对 600s 没有内存收益。
- **按 epoch 失效、TTL 设 1h 兜底**：内存风险等同于「长时间无写入时 key 常驻」；与管理台
  的刷新节奏相比，600s 已足够，保留一个可预期的回收上限更稳妥。

## 后果

- 打开管理台、偶尔刷新都能直接命中，不再每次先付 0.5s；数据变更仍即时可见。
- `audit` 的「陈旧」边界最多滞后 10 分钟；该字段本就是检出时刻语义，不另做事件时间。
- 夜间批量写仍会频繁换 epoch，命中率下降的原因不变，与本次 TTL 调整无关。
